# Decisions

One line of rationale per decision. Newest at the bottom.

| # | Decision | Rationale |
|---|---|---|
| 1 | **Gemini (google-genai SDK) is the LLM**, not Claude. | Owner's choice. Wherever the brief says "Claude", read "the LLM". The architecture stays the same: the LLM only extracts and classifies, and code decides. |
| 2 | LLM output is constrained with Gemini **structured output** (JSON schema from pydantic), then re-validated with pydantic. | Gives the same guarantee as a forced schema tool, and the extraction calls get no tools at all, so injected text has nothing to trigger. |
| 3 | Tax-rule learning runs in **two calls**: (a) a Gemini + Google Search call that only returns candidate URLs, then (b) our code resolves redirects, keeps allow-listed hosts, fetches the page, and runs the injection scan; then (c) a separate no-tool call extracts the rule from that page text. | Gemini search grounding has no domain allowlist, so the allowlist is enforced in our code. The call that reads the untrusted page has no tools. |
| 4 | **USA (EIN) is the first-seen country.** EIN is therefore *not* a seed rule. Singapore UEN is pre-warmed as the backup, and Chile is the poisoned-search scenario (S5d). | Owner's choice. The US is learned live from irs.gov-type sources. |
| 5 | India (GSTIN + PAN) is the home country for the happy path. | Default from the brief. India has the richest checks (checksum, GSTIN↔PAN, PAN entity code). |
| 6 | **Render free tier, no persistent disk.** SQLite lives on ephemeral disk, and every cold start re-seeds. | Demo only. A side benefit: each fresh boot makes the US "first seen" again. Ping the URL before a demo, because free instances sleep and lose data on spin-down. |
| 7 | Vendor emails can be **sent for real via Resend** (`EMAIL_PROVIDER=resend`). `EMAIL_REDIRECT_TO` routes every vendor email to one inbox, and an `Idempotency-Key` is set to the outbox id. | Owner asked for real delivery. Resend only delivers to the account owner until a domain is verified, and sample vendors use fictional addresses. A send failure is shown on the email and never changes a decision. Internal briefs are never sent. |
| 8 | `LLM_MODE` defaults to **replay** in code (`.env.example` documents live). | Safe default: the app runs with no key and never spends budget by accident. |
| 9 | The audit log is append-only, **enforced by SQLite triggers** as well as by having no update/delete code. | Defence in depth. "Reset demo data" deletes the database file instead. |
| 10 | Plain `sqlite3` + pydantic, no ORM. One short-lived connection per unit of work, WAL mode. | Fewest moving parts. The data volume is tiny. |
| 11 | Severity gains a `soft` level (risk points only) next to info/fixable/escalate/reject. | The catalogue's soft codes (FREE_EMAIL_DOMAIN, etc.) need a severity that adds points without forcing a route. |
| 12 | Without `DEMO_PASSWORD` the login gate is off (local dev). With it, a signed cookie is used. | One-command local run. The deployed instance always sets the password. |
| 13 | New escalate code **CHECK_MISSING**: a required check that is absent, skipped, or warned (without its own blocking code) escalates. | "A missing check counts as a failure", and an unexplained gap is a human's call, not the vendor's. |
| 14 | New fixable code **BANK_DETAILS_INVALID** for account/IFSC/ABA/IBAN format or checksum failures. | The catalogue had no code for a mistyped bank number. It is innocent and fixable, like a tax ID typo. |
| 15 | New escalate code **TAXID_INCONSISTENT** when the PAN embedded in the GSTIN differs from the PAN on the documents. | The identifiers contradict each other, which suggests documents from another entity. That is suspicious, not a typo. |
| 16 | A *fuzzy* hit on a *blocked* watchlist entry emits **WATCHLIST_HIGH** (escalate), with the explanation saying so. | The brief says fuzzy watchlist hits are escalate-only and never reject. This reuses the escalate code instead of inventing one. |
| 17 | Required checks must be exactly `pass`. A required check that passes "with a note" (e.g. names agreed by code + LLM) is `pass` with `warn_note` in its evidence. | Keeps INV-1 crisp: approval needs every required check to pass. |
| 18 | "Within edit distance 1" is implemented as: a **single-character substitution** exists that makes the ID fully valid (format + checksum). | Captures typos without guessing insertions or deletions. It is cheap (≤ len × 36 probes). |
| 19 | Dotted acronyms collapse during name normalisation ("S.A.S." → "sas", "F.Z.E." → "fze"). | Without it, legal forms written with dots never matched their undotted spelling (caught by a sanctions test). |
| 20 | Both LLM roles default to **`gemini-3.5-flash-lite`**, with `thinking_level=low`, `temperature=0`, `store=False`. | Benchmarked on the same document: 3.8-flash took 4–25s with 45s+ timeouts, 3.6-flash spiked to 72s, while 3.5-flash-lite was consistently ~2–5s with identical extraction quality (3.1-flash-lite missed fields). `store=False` keeps vendor documents out of server-side interaction storage. The models stay configurable. |
| 21 | **Concealed text** (white-on-background, <3pt, off-page, or fully transparent; ≥3 words) is flagged as `INJECTION_DETECTED` even without a pattern hit. Render-mode-3 text (invisible OCR layers in scanned PDFs) is scanned but not flagged by itself. | Hiding words from a human reader in a document sent to an automated system is itself an attempt to influence it. OCR layers are normal and would cause false alarms. |
| 22 | Injection LLM signals come from two places: the extraction schema's `contains_instructions` field (the model sees the rendered document), plus one `injection_llm_scan` call over the text layer, hidden text, metadata and form fields. A positive from any of them, or from the deterministic scan, sets the flag. | Covers image-only content (seen only by the extractor) and hidden text (seen only by the text scan) with few calls. |
| 23 | Untrusted text placed in prompts has `<` and `>` replaced with look-alike angle quotes. | A vendor cannot close our `<untrusted_text>` wrapper and talk to the model "outside" it. |
| 24 | Sample PDFs are generated with reportlab `invariant=1` (no timestamps). | Byte-identical regeneration keeps recording keys (which include file hashes) valid. |
| 25 | Every generated document carries a "FICTIONAL SPECIMEN" footer and specimen issuer names. | No sample should pass for a real government or bank record. |
| 26 | New escalate codes **BANK_DETAILS_MISMATCH** (form account ≠ bank-letter account) and **COUNTRY_MISMATCH** (documents or address name another country). | Both are classic diversion patterns and not innocent typos, so a person decides. |
| 27 | A check that cannot run because an upstream check failed is `skipped` with a structured **`blocked_by`** field. The engine accepts it as covered only if the named check really failed with a blocking code. | Stops a fixable failure (wrong document) from also producing a misleading `CHECK_MISSING` escalation, without letting a skip excuse itself. It is a field, not evidence text, so INV-2 still holds. |
| 28 | **Facts vs judgements on re-runs:** file validity, text layers, extractions (by file hash) and the tax rule are always re-established. Only check *results* are reused when their inputs did not change. Risk and injection checks always re-run. | Reusing a result must never leave later stages without the data they need. Watchlists and sanctions change over time, and these checks are cheap. |
| 29 | Downstream checks only use an extraction whose `doc_type` check **passed** (`ctx.usable`). | Values read from a wrong or unreadable document must never feed name, tax or bank comparisons. |
| 30 | Runs interrupted by a restart are closed on boot as `pending / manual_review` (CHECK_MISSING). | A run can never hang or silently approve after a crash or redeploy. |
| 31 | Allowed changes on a resubmission = the inputs of the checks we asked the vendor to fix (missing fields only for FORM_FIELD_MISSING; a new bank letter allows new bank fields). Anything else changed → UNREQUESTED_CHANGE. | Lets the vendor fix what was asked without false alarms, while catching the classic "also swap the bank account" move. |
| 32 | The local preview server runs with `DEMO_PASSWORD=""` and its own `data-preview/` folder (see `.claude/launch.json`). | Developer convenience only; deployed instances always set the password. |
| 33 | Reviewer actions live in `app/review.py`: approve/reject (typed reason required), request info (choose from the case's fixable findings or a re-upload of any document), clear a near-match hit, and add to the watchlist (every identifier offered). Approving a case flagged for injection or sanctions requires an explicit "I have inspected the flagged content" confirmation, enforced on the server. | Keeps every human override explicit and auditable. Exact sanctions matches can never be cleared. |
| 34 | A cleared hit stays cleared for **that submission** on later runs (the evidence says who cleared it and why). It is not suppressed for any other submission. | Avoids re-flagging what a person already resolved, without weakening screening for anyone else. |
| 35 | Reminders go out on day 3 and day 7 after the request. Auto-close at `AUTO_CLOSE_DAYS` sets the status to `rejected` with `closed_reason=auto_closed_no_response`. The scheduler runs when the simulated clock moves, on boot, and when the Awaiting vendor page opens. | The brief's three statuses have no "closed"; the reason field distinguishes a time-out from a risk rejection. No background worker is needed for a demo. |
| 36 | Bank change on an approved vendor: payment hold, a `bank_change` run (unchanged results reused), `BANK_CHANGE_REQUEST` (escalate), and case tasks to call back the phone **on file**. Approve updates the bank details and lifts the hold. Reject keeps the old verified details and lifts the hold. | Mirrors standard payment-fraud controls. The vendor only ever sees the neutral holding notice. |
| 37 | An optional `contact_phone` form field was added. | Gives the callback task a phone on file and lets watchlist phone identifiers match. Optional, so existing samples and recordings are unchanged. |
| 38 | The vendor portal sits behind the demo password (decision from P0). The "attach corrected files from sample" helper is a clearly labelled demo convenience that only fetches sample files. The pipeline never knows where a file came from. | Lets an evaluator run S7a/S7b in two clicks without breaking the "no keying off sample names" rule. |
| 39 | **Gemini Google Search grounding currently returns 429 (no quota) on this API key**, while plain calls work. Search is pluggable: `gemini` (live search) falls back automatically to `directory`, a short curated list of official tax-authority URLs that are fetched live, injection-scanned, read by the LLM and self-tested. `fixture` is for tests and S5d. The live view and evidence say which path was used. | Learning still runs live and honestly without grounding quota. Enabling billing on the key makes the live search path work with no code change. |
| 40 | The allowlist is checked on the **final hostname after redirects** (`host == d` or `host.endswith("." + d)`). Non-allowlisted links are never fetched; Gemini's own citation redirector is the only exception, and its target is still checked. | Gemini grounding cannot be restricted by domain. Matching on hostnames defeats look-alikes such as `irs.gov.evil.example`. |
| 41 | Examples used in the self-test must appear **verbatim on the source page**. If the page only prints a template (IRS: "XX-XXXXXXX"), the template must be verbatim on the page and code turns it into a synthetic example, labelled as such in the evidence. | Stops the LLM from inventing examples that would make any regex "pass". Many official pages give a template, not real numbers. |
| 42 | Long pages are reduced to windows around the identifier's name (≤20k chars), and PDFs are converted to text with PyMuPDF. | IRS Publication 1635 is a 36-page PDF; a plain head-truncation could miss the format statement. |
| 43 | Fetched pages are recorded and replayed with the LLM mode (`recordings/pages/`). | Tests and the offline demo never touch the network. |
| 44 | Only genuine misses (not found, failed self-test, rejected for injection) go into the 24h negative cache; errors (LLM down, network) do not. | An outage should not block learning for a day. |
| 45 | A poisoned web source never sets the *vendor's* injection flag. It is rejected at the source and the run ends in `TAX_RULE_UNAVAILABLE` (manual review), with the rejected sources listed in the evidence. | The vendor didn't inject anything. The outcome is still "never approved", and the reviewer sees why. |
| 46 | "Forget rule" (learned rules only) deletes the rule and its search log so first-seen learning can be demoed again. It is audited, and seed rules cannot be forgotten. | Demo repeatability without resetting everything. |
| 47 | "Auto-decided" = the submission's current outcome came from the rules engine without a person: approved, rejected, or sent back to the vendor. Manual-review cases and reviewer decisions are not auto-decided. "Median time to decision" = submission created → first approve/reject decision. "Cache-hit rate" = tax-rule lookups answered by the registry ÷ all fresh lookups (reused results excluded). | Plain definitions a procurement manager can check against the table. |
| 48 | Dashboard charts are plain HTML/CSS (no chart library): a single-hue bar chart for reason codes, and stacked bars by day using the four status colours (validated with the dataviz palette checker: all CVD checks pass, and amber's low contrast is covered by text labels in the legend plus a table view). Every mark has a hover/focus tooltip. | Fewer moving parts. Colour is never the only carrier of meaning. |
| 49 | The drawer loads a server-rendered fragment (Jinja autoescape) via fetch. The same template backs `/submissions/<id>` for deep links and no-JS use. Checks are sorted problems-first. | One escaping path for untrusted values (INV-4). Reviewers see what matters first. |
| 50 | The audit trail ties together everything about a submission, including LLM calls (tagged with the run via a context variable), emails prepared, review cases opened and decisions. | "Who or what did what, when" for one vendor on one screen. |
| 51 | The watchlist page supports manual entries, CSV import (rows sharing a label become one entry), and deactivate/reactivate with a reason, plus match history per entry. Deactivated and expired entries are not screened. | Lists need curation outside review cases; every change is audited. |
